- (direction) Positioning: a built-in, ready-made way to read the wiki. Not framed as an Obsidian replacement. Reason to exist: it understands Lumina data (typed edges, entity types, communities, citations), where a generic markdown graph sees only plain links.
- (note) Wiki mode has no view today; `view` exists only in project mode under `src/project/`. README mentions opening the workspace in Obsidian as an optional suggestion.
- (decision) Read-only in this phase, no editor. The agent edits the wiki; the human reads it.
- (decision) Layout is three panes, mirrored from Obsidian on purpose: graph on the left as the primary surface, page tree on the right, reader in the middle appearing when a page is opened.
- (decision) Entry point is a `/lumi-view` skill, same pattern as `/lumi-project-view`: the agent runs a command that assembles the page and opens it.
- (decision) UI is built with React 19 (19.3.0 current on 2026-10-10). Pinning React 18 rejected: 18.3.1 dates from 2024-04 and React 19 ships no UMD build, so a no-build React route means a dead pin.
- (decision) Built as a separate viewer from the project-mode one and more capable than it. Inherits its graph styling only, plus the vendored force-graph and Node-side community detection where they fit.
- (decision) Two steps kept apart: code is bundled once at publish time with esbuild by the maintainer; the page is assembled on the user machine on each run with plain Node, inlining the prebuilt bundle and the wiki data. No bundler on user machines: esbuild is a 10.6 MB native binary with its own postinstall.
- (decision) Static self-contained HTML opened via file:// first, no local server. A server is reconsidered only if users complain about having to refresh.
- (constraint) devDependencies are allowed for the viewer build only. CLI, installer and scripts keep shipping as authored source. Runtime dependencies, no postinstall, no native modules on user machines, cold start under 300 ms and zero telemetry are unchanged.
- (constraint) Logic lives in plain .mjs modules tested by `node --test`; the React layer stays thin. No Jest or Vitest.
- (question) What must the reader render in v1: tables, code highlighting, math?
- (question) Does the built bundle live in git, or is it built in `prepack`?
- (question) Does project mode later move onto the new viewer?
- (note) Inspection of `src/skills/**` and `src/templates/**`: page templates prescribe frontmatter, headings, bullets, bold, inline quotes with locators like (p. N), wikilinks, and HTML comment markers. No skill prescribes math, tables, fenced code, diagrams, images, callouts or footnotes in page bodies.
- (note) Wikilink forms in use: `[[slug]]`, path-qualified `[[type/slug]]`, and `[[slug|alias]]` (accepted by lint). Slugs are unique per entity folder, not wiki-wide. Lint resolves them in `resolveWikilinkTarget`: exact slug, then unique basename; an ambiguous bare name does not resolve.
- (note) Graph data: `wiki/graph/edges.jsonl` lines `{from,type,to[,confidence]}` with confidence high|medium|low; symmetric types stored once; terminal types have no reverse; targets may be external URLs with no page. `wiki/graph/citations.jsonl` holds source-to-source `{from,type:"cites",to}` rows only. No `wiki.mjs` read command emits the full node and edge set.
- (note) Project-mode `view` prints `{ok,file,url}` and nobody opens the browser; its skill forbids starting a server. Classic install copies `src/scripts/` top-level files from an explicit array in `copyScripts`; `package.json` `files` is a per-file allowlist; no `prepack`, `prepare` or `prepublishOnly` exists; publish runs from a `v*` tag in `.github/workflows/publish.yml`.
- (decision) Open question on reader scope resolved from the inspection: v1 renders standard markdown (headings, lists, emphasis, block quotes, links, tables, plain code blocks). Math, syntax highlighting, diagrams and embedded images are out of this iteration.
- (decision) Open question on project mode resolved: moving the project-mode viewer onto the new one is a non-goal for this iteration; the project-mode viewer and its output stay unchanged.

- (note) Host research: Claude Code sandbox is off by default and its docs say detached children are stopped at session exit. - (note) Comparable tools: GitNexus and Prisma Studio have the user start a foreground server from a terminal. claude-mem starts a detached daemon from agent hooks and has issues about orphan processes and stale ports. Serena had CVE-2026-49471: an unauthenticated dashboard with no Host check allowed DNS rebinding. None of them works from file://.
- (decision) The server runs in the foreground only. No daemon, no detached child, no state file, no idle timer. Whoever starts it owns its life: the agent host as a background task, or the user in a terminal. Where a host cannot start or keep it, the skill gives the user one command to run. Supersedes the detached-with-idle-exit idea, which the comparables show is where orphan and port pain comes from.
- (decision) Server protection, from the Serena advisory: bind 127.0.0.1 only, reject any request whose Host header is not its own loopback address, GET only, send no CORS headers, resolve every file path through safePath, serve only wiki pages and its own assets.
- (decision) The built viewer bundle is committed to git. CI rebuilds it and fails on any difference, on every pull request and before publish. If Linux CI produces different bytes than macOS, fall back to building in prepack with an asset assert. Resolves the open question on bundle location.
