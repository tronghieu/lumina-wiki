topic: Lumina project-docs overlay mode (vs graphify)
goal: Decide whether and how Lumina should turn a software project's existing docs into a typed, checked, queryable graph for humans who manage agents and make decisions
mode: partner
status: complete

- (direction by user) Need: in software projects humans rarely read code now that agents write it; they care about high-level docs. Question: what would a Lumina option for projects offer over graphify (Graphify-Labs/graphify)? Stay at idea level, no implementation.
- (insight by coach) graphify is a map of code: derived, regenerable, always true to current code, no memory. Lumina must not compete on code structure (AST, call graphs, zero-effort, multimodal).
- (insight by coach) Lumina's edge is project memory: why decisions were made, what superseded what, typed schema, lint, human-readable markdown in git. Real competitors are DeepWiki / Google Code Wiki (auto-generated code wikis), not graphify.
- (insight by coach) Biggest risk is doc rot: docs claim X while code does Y. Killer feature candidate: drift detection between doc claims and code evidence (graphify/AST as ground truth).
- (decision by user) Focus on documentation only, not code.
- (decision by user) Auto-update via hook: on change, scan the configured doc folders and refresh the graph.
- (decision by user) Primary reader is humans on the project, mostly people who manage agents or make decisions.
- (decision by user) Ship as a separate install mode, like the existing --agents openclaw/hermes target, not a content pack.
- (decision by user) No second source of truth: existing project docs stay canonical; Lumina only graphs them into a structured ontology and must not create duplicate markdown pages.
- (insight by coach) Survey Seli: ~1140 content .md; docs/ 234 (adr 63, conventions 25, workflows 24, features 20, data-models 13, tech-debt 9...), _bmad-output/ 745. Uniform frontmatter type/id/status/related. IDs ADR-0009, FR6.7a, TD-0001, C001, Story 7.3. graphify-out/ already present.
- (insight by coach) Survey Capigo: ~1400 content .md; docs/ 440 (user-guide 121, adr 95, features 79, workflows 49...), _bmad-output/ 936. 95 ADRs have no frontmatter (status in '## Status' body). IDs ADR-088, FR-WMS-22-9, CAP-N, SPEC-*, C020. Existing checkers: check-frontmatter.mjs, dead-link, ADR-number. graphify-out/ present.
- (insight by coach) Both projects already hold an implicit ontology (frontmatter, ID schemes, related links, doc-precedence rules in docs/README.md). Lumina's job: make it explicit, checked, queryable, while writing nothing into the docs.
- (insight by coach) Real pains a graph fixes: Seli FR renumbering hand-propagated across 47 files; Seli ADR-0009 partially superseded by ADR-0052; Capigo duplicate QA gate IDs (1.20-... vs 1.20....); precedence rule 'ADR wins' encodable as ontology rule.
- (idea by coach) Three layers, none writes to docs: (1) per-project mapping config, (2) derived graph with file:line provenance and extracted/inferred edge tags, reverse edges only in graph, (3) cross-doc lint + ask. Lumina reports; fixes are made in the source doc.
- (idea by coach) Decision history comes from git: diff the graph between commits, no timeline pages written.
- (idea by coach) Hook in two tiers: deterministic tier (frontmatter, IDs, links) on every change; LLM tier (relations from prose) on demand or batched, always tagged inferred.
- (idea by coach) Human channel: chat via agent answering from the graph; secondary read-only generated views (traceability, violations) that only aggregate and point to sources, so they are not a second truth.
- (insight by coach) Overlay mode inverts core invariants (bidirectional links written to pages, wiki.mjs as sole page writer, timeline/compiled zones, raw/). Reusable: schemas engine, graph, lint, lumi-ask, lumi-verify, lumi-hub. Honestly a second product on the same engine.
- (insight by coach) Risks: per-project mapping cost (ID regexes differ); validated only on two projects by the same designer sharing BMAD taxonomy; overlap with Capigo per-file checkers (Lumina should do cross-doc checks only); noise from test artifacts.
- (question by coach) Open: should the derived graph be committed to git? Coach recommends no (treat like graphify-out/).
- (question by coach) Open: allow the LLM tier in v1? Coach recommends deterministic tier only first.
- (decision by user) Source folders are configurable; default is docs/, so _bmad-output/ can be skipped.
- (insight by coach) Default docs/ consequences: FR IDs are defined in _bmad-output PRDs but cited in docs/ -> declare them as external_ids (node exists, no definition, lint only checks pattern). FR->Epic->Story->QA gate traceability is lost unless subfolders are added. Capigo docs/user-guide (121) should be excluded.
- (decision by coach) Pilot recommendation switched to Seli (234 docs, uniform frontmatter, deterministic tier covers nearly all); Capigo second to test ADRs without frontmatter.
- (decision by user) Support multiple glob patterns for include and exclude source folders.
- (idea by coach) Glob rules: in scope = matches >=1 include and 0 exclude, exclude always wins, no '!' negation; only '*' and '**' via existing src/scripts/lib/globs.mjs matchGlob; bare dir 'docs' means 'docs/**'; paths repo-relative through safePath().
- (idea by coach) Always-excluded (not overridable): .git/, node_modules/, _lumina/. Default-excluded (overridable): .agents/, .claude/, .agent/, .trae/, .codex/, .serena/, graphify-out/.
- (idea by coach) Hook and scanner share one matcher (lesson from globs.mjs header). Warn when an include pattern matches zero files. Skip .gitignore support until a project needs root-wide include.
- (idea by coach) Example config: Seli include [docs]; Capigo include [docs, packages/*/docs], exclude [docs/user-guide, docs/templates] (templates carry placeholder IDs that would create fake nodes).
- (direction by user) Asked whether the ontology should be user-configurable.
- (idea by coach) Ontology in three tiers: core semantics fixed in code as pure data (edge types + their lint rules + canonical statuses); mapping configurable by user (dir/type -> entity type, ID regex, frontmatter field -> edge type), proposed by agent at init; extension (custom edge types/lint rules) deferred.
- (idea by coach) Core entities: decision, requirement, feature, workflow, data-model, convention, tech-debt, component, fallback doc. Core edges with lint: supersedes (partial flag; acyclic; target status superseded; flag citers), governed-by (flag if decision superseded), addresses (to requirement, may be external), enforced-by (script must exist), part-of (component/app), references (default, no rule).
- (idea by coach) Untyped 'related:' frontmatter: infer edge type deterministically from the (source type, target type) pair declared in config, e.g. feature->decision = governed-by, decision->requirement = addresses, default references.
- (insight by coach) Defer custom edge types: both pilots fit the core; per-project semantics would break lumi-hub cross-wiki queries; a custom edge without a lint rule is just references renamed.
- (insight by coach) Capigo ADR status lives in body '## Status'; mapping needs a status source option (e.g. status_from heading 'Status'). Only place in the two projects where frontmatter is insufficient.
- (decision by user) Provide a setup skill for project mode: it scans the project, warns and proposes to the user (folders, mapping, ontology), including frontmatter problems such as Capigo ADRs without frontmatter.
- (direction by user) Asked to weigh the risk of Lumina competing with DeepWiki and Google Code Wiki.
- (insight by coach) Research (2026-09): DeepWiki and Google Code Wiki are code-only, generate their own prose, live in vendor cloud, regenerate wholesale, no typed ontology, no ADR supersession, no doc-to-doc lint. DeepWiki has MCP (mcp.deepwiki.com); private repos paid-only since Jul 2026. Code Wiki public repos only; local Gemini CLI extension still pending.
- (insight by coach) Direct overlap with the docs-as-truth overlay is low. Substitution risk is medium: if managers are satisfied with 'what the system does' from a code wiki, they skip docs. Lumina must stay on the 'why / decided / required / conventions' layer that code cannot reveal.
- (insight by coach) Absorption risk: ingesting existing docs/ADRs is a small step for DeepWiki (.devin/wiki.json) or Code Wiki's local extension, but typed ontology + cross-doc lint is niche for them. Moat is not tech: docs stay truth and nothing is written, local/OSS/no vendor cloud, lint tied to project semantics, works inside any agent host via skills.
- (insight by coach) Closer threats than DeepWiki/Code Wiki: graphify already parses docs locally with EXTRACTED/INFERRED edges and MCP (could add a docs-ontology mode); Swimm already owns doc-to-code drift detection (patented), so drift is not a unique differentiator; log4brains covers ADR supersession for ADRs only.
- (insight by coach) Biggest competitor is no tool: an agent grepping docs/ ad hoc. Graph must beat it on completeness, determinism, cost, and continuous lint in hook/CI.
- (insight by coach) Market-size risk: value requires docs that already carry frontmatter and IDs; Seli/Capigo are atypical (heavy BMAD). The setup skill's frontmatter proposals are what widen the market.
- (idea by coach) Do not build in v1: code wiki generation, hosted UI, doc-to-code drift. Position as 'graphify for code, Lumina for docs'.
- (idea by coach) Pilot kill criterion: on Seli, collect ~10 real manager questions and lint cases; continue only if graph+lint clearly beats agent-with-grep on most of them.
- (decision by user) Do not commit the derived graph: installer adds _lumina/graph/ to .gitignore; commit only the mapping config (the real Lumina source of truth). Reasons: deterministic rebuild is sub-second, graph files cause daily merge conflicts across parallel agent worktrees, a committed graph goes stale when hooks are skipped (a second truth), history is recoverable by rebuilding at any commit.
- (idea by coach) Query checks doc hashes and rebuilds when stale, so the graph is never stale even without the hook; hook becomes an optimization; CI lint always rebuilds from scratch.
- (question by coach) Deferred until the LLM tier exists: whether to commit a cache of inferred edges keyed by content hash (costly and non-deterministic to regenerate).
- (direction by user) The LLM is always there: it is the coding agent. After install the user opens the agent and calls a setup/init skill that scans the project, detects frontmatter issues and proposes the ontology.
- (direction by user) Challenged that nodes are whole files; asked whether scanning frontmatter alone is enough to build the ontology.
- (insight by coach) Admitted file-as-node was too coarse. Node granularity: document, ID/anchor-addressable fragment inside a doc (a requirement line, a row in a decision status table, an entity in a data-model doc), and domain concept (term spread across docs, no file of its own; node holds name, aliases, mentions only, no prose; points to the project glossary if one exists).
- (direction by user) Do not lock onto Seli or Capigo: other projects may lack workflows or have doc structures those two lack. That is exactly what the ontology is for. The agent must be guided by the ontology to ingest docs, not just read frontmatter.
- (decision by user) Ontology in two tiers. Meta-ontology fixed in Lumina, about the nature of project knowledge, not folder names: Decision (lifecycle), Requirement/Goal, Rule/Constraint, Capability, Process, Structure, Concept, Actor, Issue, Evidence, plus Document as container. Meta-relations carry lint semantics: supersedes (acyclic, target status), satisfies (flag unsatisfied requirement), governs (flag superseded governor), depends-on / part-of (flag cycles), justified-by, owned-by, contradicts (always flag), mentions, references (default, no rule).
- (decision by user) Project ontology is proposed by the agent at setup from what the project actually has; each project type declares its meta-type (ADR is-a Decision, Runbook is-a Process, KEP is-a Decision, Postmortem is-a Issue). Custom types are allowed as long as they map to a meta-type; this supersedes the earlier 'defer custom edge types' and the Seli/Capigo-derived core entity list. Lint and lumi-hub cross-wiki queries key on meta-types.
- (decision by user) Ontology-guided ingest: the ontology is the agent's instruction (like /lumi-ingest with a schema). Per doc the agent extracts entities, IDs/anchors and relations; every fact carries an evidence quote and file:line. Sources by cost: frontmatter/links/IDs (deterministic parse), document structure (headings, tables, lists, diagrams; agent), prose (agent). The graph holds typed relations and pointers only, no prose, so it is not a second truth; /lumi-verify checks evidence quotes still exist.
- (decision by user) Withdrawn: 'LLM proposes, writes back into frontmatter, graph stays deterministic'. Frontmatter cannot express fragment-level entities and most projects will not accept bulk agent edits. Write-back remains only for frontmatter fixes the user wants.
- (decision by user) Revised graph-commit decision: split the graph. Parsed part (frontmatter, links, IDs) is not committed (rebuildable). Agent-extracted part is committed as one file per source document keyed by content hash, so the team does not re-pay ingest, CI can lint, and conflicts only occur when both branches edit the same doc (which conflicts anyway).
- (decision by user) Hook role revised: the hook cannot run the agent; it rebuilds the parsed part and marks facts stale when a doc hash changes. Queries warn how many docs changed since last ingest. The real update runs via /lumi-ingest or a scheduled OpenClaw/Hermes job.
- (decision by user) Question 'LLM tier in v1' is closed: agent-guided ingest is the main path in v1; deterministic parse is the fast path.
- (idea by coach) Validate generality beyond BMAD: add a third pilot with a different doc structure, e.g. Kubernetes KEPs (kep.yaml, clear lifecycle) or Rust RFCs.
- (decision by user) Provide a graph view for humans to browse nodes and relations, with an Obsidian-like graph view UI (the look and interaction, not opening in Obsidian). No Obsidian vault export.
- (decision by user) Viewer is a self-contained HTML page (e.g. _lumina/graph/view.html), regenerated on each build, gitignored, data embedded inline so file:// works. Built on vasturiano force-graph (2D, canvas) used directly; no React. 3D (3d-force-graph/three.js) only as a later option.
- (idea by coach) Viewer features: animated force layout with drag/zoom/pan, node size by degree, hover highlights neighbors and fades the rest, color by meta-type with legend, settings panel (filters by type/status/folder, orphans toggle, force sliders), local graph (N hops from a node), search. Lumina-specific: edge type labels and directional arrows/particles, lint violations and stale facts highlighted, detail panel with evidence quote and vscode://file/...:line link.
- (idea by coach) Constraints: canvas not SVG (thousands of nodes); library vendored into the package, never loaded from CDN (zero-telemetry rule 10), check ci-package allowlist; viewer generation lazily imported to keep cold start under 300 ms.
